# درس ۱۹ — بازبینی، تست و تکمیل پروژهٔ User Management

## هدف درس
تا درس ۱۸ عملیات CRUD را طراحی کردیم. در این درس یاد می‌گیریم چطور رفتار توابع را به‌صورت منظم آزمایش کنیم، خطاهای رایج را پیدا کنیم، و کد را برای تغییرات بعدی قابل‌اعتمادتر بسازیم.

> نکته: پروژه فعلاً از آرایهٔ درون حافظه استفاده می‌کند. این مرحله هنوز API HTTP یا پایگاه داده ایجاد نمی‌کند.

## ۱. تست یعنی چه؟
تست بررسی می‌کند آیا کد برای ورودی مشخص، خروجی و اثر مورد انتظار را تولید می‌کند یا نه. فقط یک بار اجرا کردن برنامه کافی نیست. برای هر قابلیت باید حالت موفق، حالت نامعتبر و حالت مرزی را بررسی کنیم.

مثلاً برای `getUserById`:
- شناسهٔ موجود باید کاربر درست را برگرداند.
- شناسهٔ ناموجود باید طبق قرارداد `null` برگرداند.
- نوع نامناسب شناسه، مثل رشته به جای عدد، باید طبق تصمیم طراحی مدیریت شود.

## ۲. دادهٔ آزمایشی
در فایل `users.js` می‌توانیم دادهٔ اولیهٔ پروژه را داشته باشیم:

```js
export const users = [
  { id: 1, name: "Ali", age: 20, role: "admin", isActive: true },
  { id: 2, name: "Sara", age: 22, role: "user", isActive: true },
  { id: 3, name: "Reza", age: 17, role: "user", isActive: false },
  { id: 4, name: "Mohammad", age: 25, role: "admin", isActive: true }
];
```

آزمایش‌ها باید از داده‌هایی استفاده کنند که نتیجه‌شان قابل پیش‌بینی است. اگر یک تست به وضعیت باقی‌مانده از تست قبلی وابسته باشد، ممکن است گاهی موفق و گاهی ناموفق شود.

## ۳. تست دستی با app.js
در مرحلهٔ فعلی می‌توانیم تست‌های دستی را در `app.js` اجرا کنیم:

```js
import {
  getAllUsers,
  getUserById,
  createUser,
  updateUser,
  deleteUser
} from "./userService.js";

console.log("همهٔ کاربران:", getAllUsers());
console.log("کاربر شمارهٔ ۲:", getUserById(2));
console.log("شناسهٔ ناموجود:", getUserById(999));

try {
  const created = createUser("Nima", 19, "user");
  console.log("کاربر ساخته‌شده:", created);

  const updated = updateUser(created.id, { age: 20 });
  console.log("کاربر ویرایش‌شده:", updated);

  const deleted = deleteUser(created.id);
  console.log("کاربر حذف‌شده:", deleted);

  console.log("پس از حذف:", getUserById(created.id));
} catch (error) {
  console.error("خطا در آزمایش:", error.message);
}
```

این نمونه فرض می‌کند توابع بالا از `userService.js` export شده‌اند. اگر نام تابع‌ها یا قرارداد خروجی در فایل تو متفاوت است، importها را با پیاده‌سازی واقعی هماهنگ کن.

## ۴. قرارداد خروجی هر تابع
قرارداد مشخص، استفاده از تابع را ساده‌تر می‌کند. برای پروژهٔ ما قرارداد پیشنهادی چنین است:

| تابع | موفقیت | مورد ناموفق |
|---|---|---|
| `createUser` | شیء کاربر جدید | پرتاب `Error` برای ورودی نامعتبر |
| `getAllUsers` | آرایهٔ کاربران | آرایهٔ خالی اگر کاربری نباشد |
| `getUserById` | شیء کاربر | `null` اگر پیدا نشود |
| `updateUser` | شیء به‌روزشده | `null` اگر شناسه پیدا نشود؛ خطا برای ورودی نامعتبر |
| `deleteUser` | شیء حذف‌شده | `null` اگر شناسه پیدا نشود |

مهم است که یک تابع در شرایط مشابه رفتار ثابتی داشته باشد. برای نمونه، `getUserById` نباید گاهی `undefined`، گاهی رشته و گاهی شیء برگرداند.

## ۵. تست حالت‌های مرزی
حالت مرزی ورودی یا وضعیتی است که احتمال خطا در آن بالاست. برای `createUser` این موارد را آزمایش کن:

```js
const cases = [
  ["Nima", 19, "user"],  // معتبر
  ["", 19, "user"],      // نام خالی
  ["   ", 19, "user"],   // فقط فاصله
  ["Nima", 0, "user"],   // سن صفر
  ["Nima", 19.5, "user"],// سن اعشاری
  ["Nima", 19, "owner"]  // نقش نامعتبر
];

for (const [name, age, role] of cases) {
  try {
    console.log("نتیجه:", createUser(name, age, role));
  } catch (error) {
    console.log("ورودی رد شد:", error.message);
  }
}
```

در کد واقعی، این تست‌ها را از اجرای عادی برنامه جدا می‌کنیم تا هر بار اجرای برنامه کاربران آزمایشی اضافه نکند.

## ۶. تست updateUser
هنگام ویرایش، باید مطمئن شویم فقط فیلدهای ارسال‌شده تغییر می‌کنند. به‌ویژه مقدار `false` یک مقدار معتبر است:

```js
const updated = updateUser(1, { isActive: false });
console.log(updated.isActive); // باید false باشد
```

از شرطی مانند `if (updates.isActive)` استفاده نکن؛ چون وقتی مقدار `false` است، شرط اجرا نمی‌شود. برای تشخیص ارسال شدن فیلد، می‌توان از `updates.isActive !== undefined` استفاده کرد.

همچنین اگر چند فیلد هم‌زمان ویرایش می‌شوند، بهتر است ابتدا تمام ورودی‌ها را بررسی کنیم و بعد تغییرها را اعمال کنیم. در غیر این صورت ممکن است یک فیلد تغییر کند و فیلد بعدی خطا بدهد؛ نتیجه، به‌روزرسانی نیمه‌کاره خواهد بود.

## ۷. جلوگیری از تغییر ناخواستهٔ داده
تابع زیر آرایهٔ تازه می‌دهد:

```js
const getAllUsers = () => [...users];
```

اما کپی سطحی است. بنابراین مصرف‌کننده هنوز می‌تواند ویژگی یک کاربر را تغییر دهد:

```js
const result = getAllUsers();
result[0].name = "Changed";
```

در این حالت شیء اصلی هم تغییر می‌کند، چون مرجع شیء مشترک است. برای این پروژه، قاعده بگذار که کد بیرون از سرویس فقط نتیجه را بخواند و تغییرات را با `updateUser` انجام دهد. بعداً می‌توانیم از کپی عمیق یا طراحی immutable استفاده کنیم، اما هر روش محدودیت و هزینهٔ خودش را دارد.

## ۸. چک‌لیست بازبینی کد
قبل از اینکه قابلیت را تمام‌شده بدانیم، بررسی کن:
- نام توابع دقیقاً نشان می‌دهد چه کاری می‌کنند.
- هر تابع مسئولیت روشن دارد.
- ورودی‌های نامعتبر پیام خطای قابل‌فهم دارند.
- خروجی توابع قرارداد ثابت دارد.
- `app.js` منطق CRUD را دوباره پیاده‌سازی نمی‌کند.
- آرایهٔ اصلی فقط از طریق سرویس تغییر می‌کند.
- تست‌ها هم موفقیت و هم شکست را پوشش می‌دهند.
- خطاها با `catch` خالی نادیده گرفته نمی‌شوند.
- نام متغیرها و تورفتگی‌ها یکدست هستند.

## ۹. اجرا و بررسی
از پوشهٔ پروژه اجرا کن:

```bash
npm start
```

اگر اجرا نشد:
1. مطمئن شو ترمینال داخل پوشهٔ `projects/user-management` است.
2. فایل `package.json` شامل `"type": "module"` و اسکریپت `"start": "node app.js"` باشد.
3. مسیرهای import با `./` شروع شوند و پسوند `.js` داشته باشند.
4. نام تابع‌های import شده دقیقاً با exportها مطابقت داشته باشد.
5. متن کامل خطا را بخوان؛ شمارهٔ فایل و خط معمولاً سرنخ مهمی هستند.

## تمرین‌های درس
۱. برای هر پنج عملیات CRUD یک تست موفق و یک تست ناموفق بنویس.
۲. بررسی کن `getUserById(999)` مقدار `null` برمی‌گرداند.
۳. کاربری بساز، وضعیتش را به `false` تغییر بده، سپس حذفش کن.
۴. تلاش کن کاربری با نام خالی بسازی و مطمئن شو خطا به شکل قابل‌فهم مدیریت می‌شود.
۵. توضیح بده چرا کپی آرایه با spread مانع تغییر ویژگی‌های اشیای داخل آن نمی‌شود.

## راهنمای پاسخ
- `createUser`: کاربر ساخته‌شده باید شناسهٔ یکتا داشته باشد؛ نام خالی، سن نامعتبر و نقش نامعتبر باید رد شوند.
- `getAllUsers`: خروجی باید آرایه باشد.
- `getUserById`: مورد پیدا نشده باید طبق قرارداد `null` باشد.
- `updateUser`: مقدار `false` باید واقعاً ذخیره شود؛ شناسهٔ ناموجود باید `null` بدهد.
- `deleteUser`: حذف موفق باید کاربر حذف‌شده را برگرداند و جست‌وجوی بعدی همان شناسه باید `null` بدهد.
- spread آرایه را کپی می‌کند، نه اشیای تو درون آن را؛ این همان shallow copy است.

## نکتهٔ حرفه‌ای
این‌ها فعلاً تست‌های دستی‌اند. در مرحلهٔ بعد می‌توانیم تست‌های خودکار بنویسیم تا اجرای تست‌ها نتیجهٔ قابل‌تکرار بدهد. در یک backend واقعی، علاوه بر تست سرویس، باید مسیرهای HTTP، اعتبارسنجی درخواست و رفتار پایگاه داده هم آزمایش شوند.

## مرور نهایی
- می‌دانم تست چه تفاوتی با اجرای معمولی برنامه دارد.
- می‌توانم برای موفقیت، شکست و حالت مرزی سناریو بسازم.
- می‌دانم قرارداد خروجی تابع چرا اهمیت دارد.
- می‌توانم خطاهای رایج import، اجرای Node.js و به‌روزرسانی داده را بررسی کنم.
- می‌دانم پروژه هنوز حافظه‌ای است و API یا پایگاه داده ندارد.
